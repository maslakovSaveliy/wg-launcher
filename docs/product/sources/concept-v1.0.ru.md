# Концепция настольной платформы для браузерных игр

Версия 1.0 · 24 октября 2026 года

Рабочее описание: независимая библиотека веб-игр с запуском по ссылке, отдельными профилями и переносом сохранений. Название продукта пока не выбрано. Этот документ описывает продукт и рекомендуемый путь проверки; это не отчёт о собранном или протестированном приложении.

## 1. Идея продукта

Пользователь устанавливает один настольный клиент, вставляет ссылку на игру и добавляет её в личную библиотеку. Игра получает карточку, отдельное окно, постоянное локальное хранилище и, по желанию, ярлык на рабочем столе. Для поддерживаемых игр клиент делает резервные копии и переносит сохранения между компьютерами.

Основной сценарий: «Нашёл игру в интернете → добавил в библиотеку → запускаю как привычную игру → продолжаю с сохранённого места».

Продукт рассчитан и на обычные JavaScript-игры, и на современные порты с WebAssembly, WebGL и WebGPU. Для запуска это веб-приложения разной сложности. Поддержка одного класса игр не гарантирует совместимость со всеми остальными.

Клиент не конвертирует веб-игру в нативный исполняемый код и не выполняет её на облачном сервере. Игра работает на компьютере пользователя в браузерном движке. Облачная часть нужна прежде всего для библиотеки и резервных копий.

## 2. Для кого и какую проблему решаем

Первая аудитория — люди, которые пробуют фанатские порты, независимые веб-игры и браузерные эмуляторы и хотят возвращаться к ним без поиска старых ссылок. Вторая — авторы веб-игр, которым нужен понятный настольный способ распространения без самостоятельной разработки лаунчера.

Основные проблемы: игры разбросаны по разным сайтам; ссылка теряется; окно смешивается с рабочими вкладками; локальный прогресс трудно перенести; непонятно, что занимает место и что будет удалено при очистке данных.

Гипотеза ценности: пользователям нужна общая библиотека с предсказуемым хранением прогресса. Предположение «люди не хотят играть в браузере» само по себе недостаточно: для многих ссылка и отсутствие установки — преимущество.

Отличие продукта должно проявляться в повторном использовании: пользователь возвращается в библиотеку, восстанавливает прогресс и запускает игру на другом компьютере.

## 3. Пользовательский опыт

1. Установить клиент и сразу пользоваться им без аккаунта.
2. Вставить HTTPS-ссылку. Клиент предлагает название и обложку, которые можно исправить вручную.
3. Увидеть карточку с кнопкой «Играть» и доступными возможностями.
4. Запустить игру в отдельном окне. Настройки окна и локальные данные сохраняются.
5. При необходимости создать ярлык, ведущий в общий клиент с идентификатором игры.
6. Включить резервное копирование для совместимой игры. Аккаунт требуется только при подключении облака.
7. На другом компьютере получить библиотеку и восстановить совместимое сохранение до запуска.

В интерфейсе нужно различать «добавлено по ссылке» и «установлено для офлайна». Полезные статусы: «Нужен интернет», «Установлена локально», «Облачные сохранения поддерживаются», «Только локальный прогресс», «Совместимость не проверена».

Универсальный лаунчер знает время сессии и дату запуска. Он не знает автоматически процент прохождения, достижения и события внутри игры. Для этого нужна интеграция с игрой.

## 4. Три режима поддержки

| Режим | Поведение | Границы обещания |
| --- | --- | --- |
| Запуск по ссылке | Открываем исходный сайт в игровом окне | Сайт и его серверы должны быть доступны; часть сайтов может не работать во встроенной среде |
| Локальная веб-сборка | Получаем полный пакет игры и запускаем локально | Требуется совместимая сборка и известные зависимости; серверные функции могут требовать сети |
| Интегрированная игра | Используем манифест, адаптер или SDK автора | Можно надёжнее поддержать сохранения, версии, офлайн и дополнительные функции |

Не обещаем автоматически скачивать любой сайт целиком. Ресурсы могут загружаться динамически, зависеть от авторизации, внешних API, серверной логики и конкретного домена. Обычный браузерный кеш не равен полноценной установке.

Загрузка локальных файлов оригинальной игры, если её требует конкретный порт, остаётся частью его сценария. Само добавление URL не заменяет такие файлы.

## 5. MVP и последующие версии

### Первая версия: библиотека и запуск

- Windows и macOS как целевые настольные платформы; сначала проверка на доступной машине, затем сборка и проверка второй ОС.
- Добавление URL, ручное редактирование карточки, поиск и избранное.
- Отдельное окно и постоянная сессия для каждой записи игры.
- Полноэкранный режим, запоминание размера окна, запуск из ярлыка.
- Учёт времени по явно определённому правилу, например только при активном игровом окне.
- Понятные действия «удалить из библиотеки», «очистить кеш» и «удалить сохранения» с разными последствиями.
- Диагностика ошибок загрузки и возможностей графического движка.
- Интерфейс экспортера сохранений и работающий экспорт/импорт хотя бы одной проверенной игры или тестовой сборки.

### Следующая версия: облачный прогресс

Аккаунт, синхронизация библиотеки, версии резервных копий, восстановление на другом компьютере, безопасное разрешение конфликтов. Ограниченный список игр с подтверждённой совместимостью сохранений.

### Затем: установка и интеграции

Локальные пакеты, докачка, проверка целостности, версии и откат. Формат манифеста для авторов и декларативные адаптеры. Linux — после проверки GPU, ввода и упаковки на выбранных дистрибутивах.

Магазин, социальная сеть, чат, достижения, моды, оверлей и мобильный клиент не входят в MVP. Их добавление должно опираться на реальное использование базового продукта.

## 6. Рекомендуемая архитектура

Начальный ориентир — Electron + React/TypeScript + отдельное ядро на Rust. Это рекомендация для проверки, а не окончательно утверждённый выбор.

| Слой | Ответственность |
| --- | --- |
| React + TypeScript + Vite | Библиотека, настройки, состояния задач, диалоги конфликтов |
| Основной процесс Electron | Окна, сессии Chromium, разрешения, узкий IPC, системные ярлыки |
| Изолированное окно игры | Выполнение стороннего веб-кода и браузерные хранилища |
| Rust-процесс | Работа с пакетами и файлами, хеширование, сжатие, резервные копии, очередь синхронизации |
| SQLite | Каталог, настройки, состояния задач и локальные сведения о версиях |
| Необязательный backend | Аккаунты, синхронизация метаданных и доступ к объектам сохранений |

Для каждой игры используется собственная постоянная браузерная сессия, например `persist:game:<id>`. Интерфейс клиента работает отдельно от стороннего содержимого. Один Chromium-дистрибутив обслуживает весь клиент; отдельный Electron-бандл на каждую игру не создаётся. Процессная модель Chromium остаётся многопроцессной.

Rust получает только необходимые команды. Первый транспорт — сообщения JSON с идентификаторами запросов по stdin/stdout дочернего процесса; логи идут в stderr. Нужны таймауты, отмена, сообщения прогресса, контроль размера запросов и восстановление после падения. Большие файлы не нужно кодировать в JSON: передаются проверенные внутренние идентификаторы или разрешённые пути.

Rust-код оформляется отдельным crate с минимальной зависимостью от оболочки. Это позволит при необходимости подключить его через napi-rs либо использовать в Tauri. Не создаём абстракцию над всеми API Electron заранее: отделяем только реальные границы ядра и браузерного runtime.

В MVP у локального каталога один владелец записи. Предпочтительно Rust-ядро; UI получает операции через IPC. Если ядро на первом этапе ещё не внедрено, не усложняем миграцию распределённой записью в SQLite из нескольких слоёв.

## 7. Electron, Tauri и другие пути

**Путь A — Electron + Rust.** Контролируемая версия Chromium, удобное управление постоянными сессиями, знакомый TypeScript-стек. Цена — размер дистрибутива, память браузерного движка и необходимость поддерживать native-сборки Rust под каждую ОС/архитектуру.

**Путь B — Tauri 2 + Rust.** Меньший собственный бандл за счёт системного WebView и прямое использование Rust. На Windows используется WebView2, на macOS WKWebView, на Linux WebKitGTK. Для игр это дополнительная матрица совместимости. Для Windows-first продукта путь особенно заслуживает проверки.

**Путь C — Tauri с CEF.** В проверенной документации Tauri 3 alpha описан CEF-runtime с поставкой Chromium. Он потенциально объединяет Rust-ядро и контролируемый движок, но требует оценки зрелости alpha-ветки. С поставкой Chromium преимущество маленького дистрибутива сокращается. Не считать этот путь готовой заменой без эксперимента.

**Путь D — собственная оболочка Rust + CEF.** Больше контроля, но значительно больше работы с окнами, профилями, IPC, обновлениями и упаковкой. Не рекомендован для первого MVP.

Выбор делается по результатам одних и тех же игровых сценариев, а не по языку или размеру пустого приложения. Смена оболочки не должна требовать переписывать файловую часть Rust.

## 8. Где Rust полезен и где не помогает автоматически

Хорошие кандидаты: обработка больших файлов, потоковые загрузки и распаковка, контроль целостности, сжатие копий, сравнение версий и фоновые очереди. Возможный набор библиотек: Tokio, reqwest, serde, SQLite через rusqlite или sqlx, BLAKE3, zstd. Версии и необходимость каждой зависимости проверяются при реализации. Это возможный набор, а не обязательный список.

Rust не ускоряет исходный JavaScript/WASM игры сам по себе и не устраняет ограничения GPU. Рендеринг, компиляция шейдеров и игровые расчёты остаются в соответствующем движке. Node.js с корректным асинхронным I/O также может быстро выполнять многие задачи.

Практические меры: не держать окна всех игр открытыми; ограничить фоновые задачи; не распаковывать большие пакеты одновременно с чувствительной к CPU игрой; виртуализировать большую библиотеку; не пересылать массивы данных через IPC без необходимости. Сначала измерять, затем оптимизировать.

## 9. Сохранения: главный технический риск

| Где находится прогресс | Как поддерживать |
| --- | --- |
| localStorage | Экспорт выбранных ключей и восстановление до запуска |
| IndexedDB | Экспорт схемы и поддерживаемых типов значений; нужно проверить транзакции, Blob и бинарные данные |
| OPFS или виртуальная файловая система | Отдельный способ экспорта; учитывать сброс буферов и жизненный цикл runtime |
| Сервер игры | Прогресс обслуживается аккаунтом самой игры; клиент не обещает его собственный экспорт |
| Только память процесса | Обычного экспорта данных недостаточно; универсальный suspend/resume не входит в концепцию |

Не нужно предполагать индивидуальный адаптер для каждой игры: общие экспортеры могут покрыть много случаев. Но заявленная поддержка появляется только после проверки восстановления. В Emscripten, например, MEMFS и IDBFS имеют разные свойства сохранности; данные могут нуждаться в `FS.syncfs()`.

Протокол синхронизации: перед запуском проверить облачную версию → получить и проверить объект → восстановить совместимую копию → запустить игру → при корректной точке сохранения экспортировать новый снимок → атомарно опубликовать новую ревизию.

Снимок содержит game_id, версию формата экспорта, версию адаптера, ревизию-родителя, идентификатор устройства, хеш содержимого и, если известна, версию игры. Время устройства используется для отображения, но не является единственным основанием выбора актуального прогресса.

Если два компьютера изменили одну базовую ревизию, сохраняем обе ветки и предлагаем выбор. Офлайн-игра разрешена; её результат синхронизируется позднее. Не применять слепую перезапись «последний по часам победил». Перед импортом — локальная резервная копия. При превышении квоты сохраняем локальные данные и объясняем ошибку.

Не синхронизируем автоматически cookies, токены, кеш ресурсов и весь профиль Chromium. Не копируем работающие базы браузерного профиля как обычные файлы. Отдельно проверяем происхождение данных: игра внутри iframe может хранить прогресс на другом origin, а изменение домена, порта или схемы может изменить доступное хранилище. Это учитывает адаптер.

Импорт из Chrome/Safari, перенос между браузером и клиентом, а также продолжение на телефоне — отдельные задачи. Первая версия обещает перенос между совместимыми настольными клиентами. Облачные сейвы не делают игру совместимой с неподдерживаемым устройством.

## 10. Установка локальных пакетов

Пакет содержит веб-сборку и декларативный манифест. Минимальные поля: стабильный game_id, версия, entrypoint, список файлов или хеш пакета, разрешённые внешние origins, требования к runtime и описание экспорта сохранений.

Запуск — через локальный сервер со стабильным origin либо правильно зарегистрированный протокол. Нужно проверить MIME-типы, WASM, workers, Range-запросы, CORS, COOP/COEP и Service Worker там, где он нужен. Не обещаем полную совместимость собственного протокола со всеми браузерными API без тестов.

Обновление устанавливается в новую папку, проверяется и затем переключается атомарно. Пользовательские данные хранятся отдельно. Откат файлов игры и откат формата сохранений — разные операции: старый движок может не прочитать новый сейв.

## 11. Безопасность как часть архитектуры

Сторонняя игра не получает Node.js, файловый доступ или общий административный IPC. Для Electron: sandbox, contextIsolation, отключённая nodeIntegration, проверка отправителя и параметров IPC, контролируемые разрешения и навигация. Не отключаем webSecurity ради запуска отдельного сайта.

У клиента и каждой игры разные границы доверия. Сервер не может передать клиенту произвольную команду ОС. Адаптеры первого этапа — встроенные и проверенные; загружаемый произвольный JS/Rust-код расширений не входит в MVP. Архивы распаковываются с защитой от выхода за каталог, симлинков и чрезмерного объёма. Загрузки имеют лимиты и отмену.

Разрешения на камеру, микрофон, файлы и устройства выдаются явно и привязаны к игре. В журналах не должно быть токенов и содержимого сохранений. Удаление игры не должно незаметно уничтожать резервные копии.

## 12. Облачная часть и модель данных

Начать с local-first: клиент работает без регистрации и сети. Backend подключается после доказанного локального экспорта/импорта. Возможный стек — знакомый владельцу NestJS + PostgreSQL и S3-совместимое объектное хранилище; конкретный провайдер пока не выбран.

Основные сущности: User, Device, Game, LibraryEntry, Installation, PlaySession, SaveSnapshot, SyncJob. У игры стабильный внутренний ID; URL может изменяться отдельно. Автоматически объединять разные ссылки в одну игру без подтверждения нельзя.

Сервер хранит метаданные и авторизацию, объекты снимков — отдельно. Нужны квоты, контроль целостности, ограниченный доступ к объектам и атомарная публикация ревизий. Клиентское сквозное шифрование — возможная дополнительная функция, но не заявленная возможность MVP.

## 13. Готовые open-source основы и конкуренция

Наиболее близкий подтверждённый аналог — itch.io app: библиотека, установка и запуск HTML5-игр своего каталога. Также существуют Xsolla Launcher для издателей и Flashpoint для архивирования веб-контента. Точный независимый аналог всей комбинации «произвольный URL + современные порты + облачные сейвы» в предыдущем поиске не подтверждён. Это не доказывает отсутствие конкурентов.

| Основа | Что использовать | Ограничение |
| --- | --- | --- |
| itchio/itch | Архитектура каталога, запуск и установка; возможный полноценный форк | Зависимости от itch.io и отдельного butler на Go; Rust не заменяет их без дополнительной работы |
| FlashpointProject/launcher | Каталог, расширения, локальные пакеты | Архивная специфика; проверенный master использовал старый Electron, другие ветки требуют отдельной проверки |
| arhitekt86/pixens-launcher | Пример React/Electron-клиента с веб-играми | Небольшой проект, часть системы вне репозитория, готовность не проверена |
| lutris/web-runner | Минимальный пример запуска URL | Не готовая библиотека и не система облачных сохранений |

Предварительно небольшой собственный клиент лучше соответствует узкому MVP по ссылкам. Форк itch имеет смысл, если сразу нужны установка, обновления и большая библиотечная инфраструктура. Окончательное решение — после сборки кандидата и оценки объёма удаления чужой логики. Лицензии основного кода и зависимостей проверяются на выбранном коммите; наличие исходников не означает отсутствия условий использования.

Нельзя строить обещания продукта на неподтверждённой полноте отдельных фанатских портов. В частности, работоспособность и полнота найденного Cyberpunk-проекта не установлены. Каталог должен состоять из реально проверенных ссылок и доступных для соответствующего распространения сборок.

## 14. Эксперименты и критерии готовности

Сначала отобрать несколько реальных игр и контролируемые тестовые сборки: JavaScript/localStorage, WASM/IndexedDB, тяжёлый WebGL или WebGPU, iframe, игра с аккаунтом или сетью. Не обязательно одна игра на каждый случай. Зафиксировать URL, дату, версию runtime, ОС, GPU и результат. Недоступная игра — недоступная проверка, а не успешная совместимость.

Проверить запуск, звук, pointer lock, полноэкранный режим, управление и геймпад там, где они поддерживаются. Сравнить одинаковые сцены с Chrome на той же машине. Измерять холодный и повторный запуск отдельно, память, CPU и плавность кадра; не переносить результаты одной машины на все устройства.

Критерии первой демонстрации:

- Добавленный URL сохраняется после перезапуска и открывается из библиотеки и ярлыка.
- Данные разных игр не смешиваются; сторонний сайт не вызывает привилегированные операции.
- Для минимум одной контролируемой или реальной совместимой игры экспорт и импорт восстанавливают проверяемый прогресс в чистой сессии.
- Сбой экспорта/восстановления не уничтожает исходный сейв.
- После закрытия игры не остаются её лишние окна и процессы.
- Если уже подключено облако, независимые изменения двух устройств сохраняются как конфликтующие версии, а не теряются.

Первые эксперименты должны дать решение по runtime, формату сейвов и способу запуска. Сроки реализации оцениваются после них; гарантий по дням и приросту FPS пока нет.

## 15. Возможная бизнес-модель

Гипотеза: бесплатный клиент с локальной библиотекой и резервными копиями; платные дополнительные объёмы облака, история снимков и удобства синхронизации. Для авторов возможны инструменты публикации и интеграции. Цены и готовность платить не исследованы.

Сначала проверяем, возвращается ли человек играть и пользуется ли сохранениями. До подтверждения этой ценности не строим магазин, платёжную инфраструктуру и большой каталог. Отдельно учитывать расходы на хранение, трафик и поддержку адаптеров: они могут расти быстрее, чем число пользователей.

## 16. Предлагаемое первое решение

Сделать ограниченный технический прототип Electron + React/TypeScript с отдельным игровым окном и постоянной сессией; проверить на тех же играх альтернативу Tauri, если доступна нужная ОС. Ядро Rust подключать к одной конкретной операции — например, упаковке и проверке резервной копии — затем расширять по реальной необходимости. Не добавлять Rust как пустой процесс ради заявления о стеке.

Результат первого этапа — работающий запуск по ссылке, доказанный локальный перенос прогресса и короткое обоснование выбора runtime. После этого проектировать облачную синхронизацию и расширять совместимость.
